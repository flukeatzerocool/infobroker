- **D59 — Fix policy and split rule.** P0 fixed in-session within at most **two files total** and 100 changed lines, one attempt; exceeding it or failing to reach green lands `LOOP OPEN`. Permitted shapes: one source/script file plus its regression test; one non-behavior-changing source file; one committed fixture plus the test assertion that pins it; or one client-artifact file plus the gate assertion that pins it. P1 scheduled on `ROADMAP.md`; P2 fixed only on a demonstrated failure; P3 record-and-close. A defect in a §4.7 REQ body or any other spec prose is **always** `Scheduled-roadmap` — this chunk does not edit `infobroker.md`.
  - **Split threshold.** Split only when Phase 1 records **more than 120 distinct enumerated anchors**, or **four or more clusters are probe-dependent**. A *distinct anchor* is one unique `file:line` after de-duplication across clusters, where a range counts once. A *probe-dependent* cluster is one whose REQs turn on runtime behavior that no existing test, fixture, or gate observes.
  - **Pre-scan (this session).** `grep -c 'REQ-'` finds 32 REQ-mention lines across the implementation and gate files, plus 8 in the skills/reference set and 12 in test headers — roughly 50 mention lines, **not** the distinct-anchor unit above. - **D60 — Cross-chunk dedup.** Open findings from closed chunks are not re-filed. F-R6-B-6 (non-`source_type` report retention), F-R6-F-4 (receipt source without retrieval time), F-R6-A-6 (`verify_report` stale/document-basis branches), F-R3-3 (KB-first response metadata), and F-R4-C-5 (`question` bypasses the KB cache) stay with their owners and are cited in the predicate cell where relevant. - **D61 — Evidence class and artifact-exempt REQs.** Classify `_Check:_` first (worklist calibration rule 1). Thirteen R7 REQs are artifact-exempt G3 per the list at `scripts/validate-spec.ts:70` (the other two entries, `REQ-091` and `REQ-101`, are R8-owned): `050–054`, `088`, `114–120`. For a **G3** REQ, reading the artifact and its gate assertion is the intended evidence — `static:` and `gate:` are legitimate classes. `REQ-125` is **G1+G3**: its G3 artifact clause is satisfied by the artifact check, while its G1 behavioral clauses (due selection, dry-run, per-topic error isolation) require a test or probe, and a G1 clause supported only by `static:` reading is a finding. Where EV4 names a test for an artifact-exempt REQ, the reviewer also opens that test (calibration rule 2): `REQ-114/116/118/119/120` have `report-contract.test.ts`, `report-modality.test.ts`, and (for 116) `report-render.test.ts`, so the artifact check is not the only evidence. `REQ-107`, `REQ-120a`, and `REQ-126` carry gate or test citations (`src/intent-citations.test.ts:1`, `scripts/validate-spec.ts:607-666`, `src/lib/report-export.test.ts:1`). Every verdict predicate cell opens with its evidence class — `gate:`, `test:`, `static:`, or `probe:`. For `REQ-125`, "the server SHALL provide a watchlist runner" is judged against the shipped runner's interface and behavior; a script-only surface is reported as a finding with the spec line, not silently accepted.
- **D62 — Read the gate's assertion, not its name.** `check-report-fixtures`, `validate-report` (unwired CLI), `check-intent-citations`, `validate-readme`, `check-skill-harness` (`scripts/test-skills/checks.test.mjs` and `scripts/test-skills/event-stream.test.mjs`, `package.json:65`), and the `validate-spec.ts` skill checks are each read line by line (worklist calibration rule 6). A gate that asserts less than its REQ states is a finding: e.g. a REQ-053 check that proves file presence but not the claimed table/diagram content. The gate-assertion read is **per cluster**, not a terminal sweep, so a verdict can be re-opened while its cluster is live.
- **D63 — Offline-only evidence.** No outbound network anywhere. Every probe runs against committed fixtures or a temp tree under `/tmp/opencode/r7-probe/` with a temp `TMPDIR`; no probe needs a config layer. One exception is in scope and permitted: `npm run test-debate-club` is a deterministic offline Arena that drives the server over stdio — it is a regression guard, not a probe, and its stdio transport does not violate this rule. The `monitor-watchlist` live path is **not** probeable here: the runner spawns the server without an `env` argument (`scripts/monitor-watchlist.ts:104-108`), and the MCP stdio transport supplies its own filtered environment, so a temp config cannot be injected and an un-injected child would resolve the real user config and could make real provider calls. Leg (b)'s live half is therefore `NOT_RUN` up front, and REQ-125's per-topic error-isolation clause is judged against the source branch plus the test, with an unobserved branch recorded as a P2 coverage finding. Any leg that would need a real provider is `NOT_RUN` with the reason.
- **D64 — Determinism.** REQ-126's determinism and the report delta's ordering are checked by running each export twice into the probe directory and comparing bytes. Probe fixtures carry fixed as-of/publication dates. Watchlist due-ness is pinned date-independently: the temp watchlist's `last_run` values are epoch (`1970-01-01T00:00:00Z`, due) and far-future (`2999-01-01T00:00:00Z`, not due), so no leg depends on the run date; the record's `ran_at` field is the only clock read and is not part of a byte comparison.

## Risks and mitigations

- **Artifact-exempt blind spot.** Thirteen REQs are artifact-checked; the mitigation is D61's rule to read the artifact check *and* any cited test, plus D62's gate-assertion reading. A REQ whose only check is "file exists" is a finding, not a pass.
- **Prose-only contracts.** Several REQs bind behavior expressed in Markdown. The mitigation is reading the gate regex and the shipped prose together; a claim in the skill that no gate or code backs is a finding.
- **REQ-125 surface ambiguity.** "The server SHALL provide a watchlist runner" may be read as an MCP tool; the shipped runner is a script. The mitigation is D61's explicit judgement step with a `spec:line` predicate, not an assumption either way.
- **Live-path gap.** The `monitor-watchlist` live path cannot be exercised offline (D63), so REQ-125's per-topic error isolation rests on the source branch plus the test; an unobserved branch is recorded as a P2 coverage finding, and no probe claims to have observed it.
- **README blast radius.** `validate-readme` is mechanical and the README step is pipeline-bound; the mitigation is to change a user-facing claim only when a shipped fix changes it, and to re-run `validate-readme` in step 23.
- **Shared modules.** `src/lib/feature-taxonomy.ts` (R9), `src/kb-receipt.ts` (R6), and `config.json` (R2) are evidence only; D66/D67 keep their defects out of the R7 register.
- **Split triggers.** Mitigated by D59's definitions and the recorded Phase 1 count; the pre-scan understates the count because it measures mention lines, so the enumeration is the authority and step 20 re-confirms.
- **P0 overrun.** A P0 exceeding D59 stops the chunk with `LOOP OPEN`.
- **Fixture drift.** `check-report-fixtures` is only as good as its corpus; the step-14 branch→fixture matrix is the mitigation and the chunk's primary finding class.

## User impact

No restart, config, dependency, or breaking change. A shipped P0 fix changes a report artifact, script, or client instruction and takes a CHANGELOG entry; otherwise the tree changes are plan/tracker/roadmap docs only. Publication stays user-authorized (D68).

## Backout

The default outcome is additive: the plan/task/AAR files, the cold-pass reports, and the tracker/roadmap edits revert with `git revert` **as a set** on the increment's commits (a per-bucket revert can leave the AAR asserting dispositions its tracker commit no longer carries); the prior trigger and verdict tables are restored together. A shipped P0 fix reverts as source/artifact plus its pinning assertion in one commit, `npm run typecheck` green before the revert is declared complete. No probe leaves state behind: every temp export, delta, watchlist record, and config layer lives under `/tmp/opencode/r7-probe/`, and the real KB, quota, and user config are never written (D63).

## Review independence

Self pass done. The cold pass is delegated to fresh `review` subagents that receive only this plan, the target file set, and the cited standards; stage reports land in `docs/plans/2026-11-09-full-review-r7/plan.cold/` and the plan is stamped `fresh` with the report path and sha256 only after stages 1–5 complete.
