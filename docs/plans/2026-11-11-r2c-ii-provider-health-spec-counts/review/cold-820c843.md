## Blockers

**B1 [design] — The stub provider is disabled in the shipped config, so the
stub traffic never happens.**
The plan's only stated setup is the URL env var: "SearXNG is
`self_hosted_http` with `url_env: INFOBROKER_SEARXNG_URL` (`config.json:220`),
so a loopback stub gives deterministic provider traffic" (`plan.md:68-75`), and
Phase 0 step 3 checks only the URL, port and env deletion (`plan.md:227-232`).
But `config.json:221` sets `"enabled": false`, `providerUsable` returns false
for a disabled provider (`src/config.ts:1130`), the health probe gate is
`registeredProvider && authOk` (`src/index.ts:1522`), and a pinned-but-unusable
provider is dropped from the chain entirely (`src/index.ts:432-434`). With the
plan as written, DB-2's successful-`search_web` leg and DB-4's three probe legs
(`plan.md:108-117`, `plan.md:130-142`) never reach the stub — and the search
falls through to the live dispatch chain instead. **Must change:** state that
the spawned test writes an isolated config with `searxng.enabled = true` (the
existing helper writes a mutable copy: `src/lib/test-isolation.ts:28-37`), and
that the URL variable alone does not make the provider operational.

**B2 [design] — A failing stub search falls back to the live provider chain,
contradicting C-4/D-6.**
With searxng enabled, a pinned provider is *prepended* to the dispatch chain
(`src/index.ts:432-433`), and a provider error advances the chain
(`src/index.ts:553-577`; the error remediation says "Trying next provider in
fallback chain"). The general_web chain is duckduckgo/marginalia/mojeek/wiby
(`config.json:245`), so the 500 leg of DB-2 and DB-4 would issue live external
requests. The hedge can also launch a second provider after 200–1500 ms
(`src/index.ts:466-469`), so even a slow success is not guaranteed
single-provider. This directly violates C-4 ("makes no external request",
`plan.md:318-319`) and D-6 ("deterministic, offline", `plan.md:360-365`).
**Must change:** specify a hermetic failure leg — an isolated config with an
empty/disabled fallback chain (or all other providers disabled) and hedging
addressed — before DB-2/DB-4 can be claimed as deterministic evidence.

## Majors

**M1 [design] — Probe eligibility is not one source; `native_fetch` flips from
inactive to active.**
DB-1 and D-5 name only `isOperational` as the eligibility input
(`plan.md:96-107`, `plan.md:356-359`), and blast radius says `assessProvider`
gains an `operational` field used by the health action. But eligibility also
depends on a registered provider: `native_fetch` is `enabled: true` with no URL
or credential (`config.json:235-242`), is absent from the provider map, and
`resolveProvider` returns undefined for a non-`generic_http` tier
(`src/providers/index.ts:69-74`). Today the health action reports it `inactive`
(`src/index.ts:1521-1541`). Under `assessProvider`, an operational provider
with no `probeStatus` defaults to `active` (`src/provider-status.ts:38-41`).
The plan does not say what `probeStatus` is passed when there is no probe
target, so a literal implementation silently changes `native_fetch`'s health
row — a change no DB clause names, against DB-8's "the health report changes
exactly as DB-1, DB-2, and DB-4 specify" (`plan.md:161-166`). Decide and record
it (either pass `inactive`, or add the flip to DB-8).

**M2 [design] — "Disabled" is not always the reported outcome, and `exhausted`
gains an unenumerated field.**
DB-1 states unconditionally that a disabled provider is "reported `inactive`
with `inactive_reason: "disabled"`" (`plan.md:96-107`). But
`resolveHealthStatus` overrides the base status to `exhausted` whenever quota
is exhausted (`src/health-status.ts:23-24`), and `assessProvider` then returns
`inactive_reason: "exhausted"` (`src/provider-status.ts:51`). A provider
disabled after exhausting its counters therefore reports
`exhausted`/"exhausted", not `inactive`/"disabled". Symmetrically, spreading
the assessment into the health report adds `inactive_reason` to `exhausted`
rows although no DB clause names that change — while C-6 and DB-8 claim
exactness (`plan.md:325-329`, `plan.md:161-166`). State the precedence and
either enumerate the exhausted field or omit it.
